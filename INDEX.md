# PrepCast Case Study — Documentation Index

## 1. Purpose and scope

Build a dbt + DuckDB dimensional model over four raw CSV extracts from **PrepCast** (a fictional
high-school sports streaming service), in order to answer one question posed by product
leadership:

> "What does *engaged viewership* look like, and how does viewership behavior relate to
> subscription retention?"

This is an **interview case study**, submitted as a ~30-minute deck plus work artifacts. The
audience is a hiring manager and a technical panel who will push on the reasoning, not just the
output.

**What this is not:**

- Not a production pipeline. Challenge 3 is explicitly discussion-and-diagram, not build.
- Not a completeness exercise. The case study states the work is scoped so that it *cannot* all
  be finished in the ~4h budget; depth on chosen parts beats a thin pass over everything.
- Not a search for a hidden right answer. "Engaged view" is deliberately undefined by the
  prompt. See `domain/engaged-view.md`.

## 3. Data sources / systems

All inputs are local CSVs in `data/`, provided with the case study. No external data or
warehouse access is needed or permitted.

| File | Rows (incl. header) | Grain per the data dictionary |
|------|--------------------:|------------------------------|
| `data/playback_events.csv` | 216,046 | One client-emitted playback telemetry event |
| `data/subscriptions.csv` | 8,015 | One subscription status/plan change (append-style log) |
| `data/users.csv` | 8,001 | One registered account |
| `data/asset_catalog.csv` | 863 | One video asset (game), LIVE or VOD |

Source-of-truth for intent: `data_dictionary_(1).docx` in the repo root. It documents what each
column is **meant** to be — the case study is explicit that reality diverges. Divergences are
recorded in `domain/source-extracts.md`, never by editing the dictionary.

The dataset is synthetic, generated by `generatedataset.py` with seed `20260716`. That script is
not provided.

**Engine:** dbt-core 1.12.2 + dbt-duckdb 1.11.0 on DuckDB 1.5.5, Python 3.14 in a
`uv`-managed virtualenv under `playon_dbt/`. Reproducible with `uv sync`. Raw is landed by
`playon_dbt/scripts/load_raw.py` as all-VARCHAR; dbt reads it as a source. Chosen over a Snowflake trial because
it costs no setup time and buys the same depth. PrepCast's real stack is Snowflake + SQLMesh;
where a modeling choice would differ between the two, note it — the panel is likely to ask.

## 4. Conventions

Naming, paragraph numbering, and footer format — see `CLAUDE.md` §4.
Work-package naming and status values — see `CLAUDE.md` §3.1.
Who decides what (design vs. construction) — see `CLAUDE.md` §9.

**Work-package numbering when more than one instance is working.** `CLAUDE.md` §3.1 says a
work-package number is never reused, which is a problem the moment two instances pick the next
free number at the same time and both write `WP-003`. So:

- A **new line of work** claims the next free integer from the table in §5 — `WP-003`,
  `WP-004`. Add the row to §5 *before* writing the file, so the number is visibly taken.
- Work that **extends or reviews an existing package** does not claim an integer at all. It
  takes the parent's number plus a lowercase letter: `WP-002a`, `WP-002b`. This is the safer
  default when you are unsure, because a suffix cannot collide with an instance reaching for
  the next integer, and it sorts next to the work it derives from.
- The suffix is not a status. `WP-002a` neither supersedes nor is subordinate to `WP-002`; it
  is a separate append-only file that happens to build on it. Supersession is still recorded
  only through the `supersedes` / `superseded_by` frontmatter keys.
- The relationship goes in the **Supersedes** column of §5 as `extends WP-00N`, and in the
  first paragraph of the work-package file.
